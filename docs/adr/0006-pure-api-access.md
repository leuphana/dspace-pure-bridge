# ADR-0006: Generated OpenAPI client for writes, hand-written DTOs for bulk reads

- **Status:** Accepted (retrospective)
- **Date:** 2026-11-02

## Context

Pure offers an OpenAPI-described REST API (version 5.31.x). The export must build complex, validated request objects (`StudentThesis`, `ResearchOutput`, contributor associations, classifications). The import, in contrast, only needs a few fields (`uuid`, `info.modifiedDate`, names and titles) for thousands of objects. Deserializing full generated models for that would be slow and fragile.

## Decision

- **Export (writes, classifications):** We use a Java client generated by OpenAPI Generator (`okhttp-gson` flavour). It is **committed to the repository** under `de.leuphana.escience.dspacepurebridge.pure.generated` (about 800 files) and treated as read-only.
- **Import and duplicate search (bulk reads):** We use Spring `RestTemplate` with small hand-written DTOs in `pure/apiobjects` (`PureWSResults`, `PureWSResult*Item`, …) and request only the needed fields (`fields=uuid,info.modifiedDate,title.*,name.*`).

Both clients authenticate with the `api-key` header. Timeouts are 60 s.

## Consequences

- The build does not need the Pure OpenAPI spec or network access. The generated code is stable between Pure upgrades.
- Updating to a new Pure API version means regenerating the client and replacing the `generated` package as a whole. Manual edits inside `generated` would be lost and are therefore not allowed.
- The repository is large (≈ 255,000 of ≈ 262,000 Java lines are generated). Code reviews and tools must exclude `pure/generated`.
- Two HTTP stacks (OkHttp for the generated client, Apache HttpClient 5 for `RestTemplate`) coexist.
- The hand-written DTOs must be kept in line with the Pure API by hand.
